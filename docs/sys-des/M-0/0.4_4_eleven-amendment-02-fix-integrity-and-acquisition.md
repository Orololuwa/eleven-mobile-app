# Eleven — Amendment 02: Fix Integrity & Acquisition

**Status:** Draft v1 (B0 + B0.1 shipped)
**Milestone:** M0
**Amends:** 0.4, 0.4.3, 0.5 (§3.9 live signal)
**Trigger:** Field session, 16 Oct 2026 — Eleven lost its GPS registration mid-run while Nike Run Club kept receiving 1 Hz fixes on the same phone; reproduced under screen lock on 17 Oct
**Evidence:** [16 Oct dropout](../../debug/2026-10-16_location-registration-dropout.md), [17 Oct lock dropout](../../debug/2026-10-17_location-registration-lock-dropout.md), `adb shell dumpsys location`

---

## B0 — Survive registration dropout (ship first)

None of the later integrity / acquisition work matters while the app is not subscribed to location. B0 is therefore ahead of everything else in this amendment.

### Problem

On 16 Oct, Eleven's GPS registration held for ~9 minutes, then dropped. After a brief churn of sub-two-second re-registrations, Eleven was **absent for the final ~35 minutes**. Nike's registration was continuous; the chip delivered clean 1 Hz fixes the whole time. The HUD showed *"Poor signal — move into open sky"* — wrong diagnosis: there were no fixes because the app was unsubscribed.

Root causes in code:

1. `processFix` called `stopLocationTracking()` on a single null / ended session lookup — a transient DB miss can unsubscribe mid-run.
2. Start and stop locks were independent — a stop can land between a start acquiring its lock and completing.
3. Nothing watched "session live" against "registration exists / fix arrived recently".
4. Live `poor` conflated "fixes arriving, quality too low" with "no fixes arriving".

### Changes

| Item | Behaviour |
|---|---|
| **Teardown policy** | Stop only on explicit `ended` / `ended_at`. A null session read skips the fix and never unsubscribes. |
| **Start/stop serialization** | Stop awaits the start lock; start awaits any in-flight stop. |
| **Watchdog** | While a session is live, every **10 s** assert that the location task is running and a fix arrived within **15 s**. Re-register on failure. Also re-check on AppState. |
| **Live signal `offline`** | Fix feed stale or missing (after cold-start settle) → `offline`: *"Lost GPS connection — reconnecting."* / `NOT A SIGNAL PROBLEM · WAITING FOR FIXES`. `poor` keeps its meaning: fixes arriving, quality/bridge failing. |
| **Registration logs** | Every start / stop / re-register logs a reason (`start`, `stop`, `watchdog`, `app-state`, `ended`, …). |

Constants: `LOCATION_WATCHDOG_INTERVAL_MS = 10_000`, `LOCATION_FIX_STALE_MS = 15_000`.

## B0.1 — Lock-safe renew (17 Oct)

B0’s watchdog still failed under screen lock and on unlock.

### Problem

1. **Stale feed + task “still running”** — Expo’s `hasStartedLocationUpdatesAsync` can stay true after GMS drops the fused→GPS request. Recovery skipped `startLocationUpdatesAsync` and only re-attached the foreground watch, so unlock did not restore fixes.
2. **`whenAppActive` inside `startLock`** — Recovery waited for AppState active while holding the start lock, freezing further starts for the rest of the locked period.
3. **Null teardown** — Repeated null session reads could still stop tracking.

### Changes

| Item | Behaviour |
|---|---|
| **Force renew** | When the fix feed is stale (or the task is down), always call `startLocationUpdatesAsync` so Expo’s `setOptions` restarts fused updates even if the task is marked started. |
| **Non-blocking recovery** | `watchdog` / `app-state` reasons never await `whenAppActive` inside the start lock. FGS-from-background errors return; unlock / next tick retries. `whenAppActive` remains only for initial `start`. |
| **AppState hooks** | `inactive`, `background`, and `active` all call `ensureLocationRegistration`. |
| **Null teardown** | Never stop on null — only explicit end. |

### Out of scope for B0 / B0.1 (later sections)

Durable dedupe, provider discrimination, cold-start acquisition, Kalman smoothing, sensor fallback, and a native AlarmManager watchdog (revisit only if B0.1 still fails under lock with logs showing force-renew attempts).
